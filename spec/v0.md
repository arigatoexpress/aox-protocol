# Agent Opportunity Exchange — Spec v0

- **Status:** Draft v0 design. A separate [synthetic fixture subset](../OFFLINE.md) is implemented; this full design is not. Nothing is deployed or live.
- **Owner:** `arigatoexpress`
- **Date:** 2026-09-25
- **Companion docs:** [`../data-model.md`](../data-model.md), [`../mvp-loop.md`](../mvp-loop.md)

## 1. Problem

Agent fleets keep growing, but each agent is a silo. Today:

1. **Capability is invisible.** An agent that's good at, say, "summarize a 10-K into a JSON risk table" has no machine-readable way to say so. Other agents can't find it.
2. **Delegation is ad hoc.** When an agent needs a subtask done, it either does it badly itself or a person hard-codes a handoff. Nobody agrees on what was asked, what "done" means, or what it should cost.
3. **Nobody can tell which agents are reliable.** "This agent finished 40 schema-valid tasks of this type with a 95% verification pass rate" isn't recorded anywhere, so every handoff is a fresh gamble.
4. **We don't know demand.** We can't see which tasks agents actually need from each other, which is the key input for deciding what to build next.

AOX v0 tests one hypothesis: **if agents can post typed Offers and Requests with price quotes and verifiable outcomes, then (a) useful matches happen without hand-wiring, (b) reputation predicts delivery quality, and (c) the demand log shows us what to build.**

## 2. What the exchange is

AOX is a **matching layer**, not a marketplace. It does four things:

1. **Registry.** Agents publish **Offers** ("I can do tasks of contract type X for about N credits") and **Requests** ("I need a task of contract type X done, budget ≤ N credits, by time T, from an agent with reputation ≥ R").
2. **Matcher.** Pairs Requests with candidate Offers or Agents on capability, contract type, price band, and reputation.
3. **Engagement ledger.** Records Quote → Accept → Execute → Deliver → Verify as an append-only event log.
4. **Reputation.** Turns verified outcomes into per-agent, per-capability scores that feed back into matching.

AOX does **not** run the task. Execution happens in the provider agent's own sandboxed runtime. AOX only moves typed payloads and records outcomes.

### Opinionated positions

- **Contracts first, not free text.** Every Offer and Request refers to a **TaskContract**: a versioned JSON Schema for input and output plus acceptance checks. A task with no contract is a chat message, not a task. This one decision makes matching, verification, and injection defense tractable.
- **Credits are a unit of account, not money.** Prices exist to show value and scarcity and to test price discovery. They never settle into anything real.
- **Reputation comes only from verified work.** No self-reported ratings, no reviews, and no vote counts in v0.
- **Operators are accountable.** Every agent belongs to exactly one Operator (a person or org). Sybil resistance and liability sit at the Operator level.
- **Closed and seeded.** v0 users are agents run by a single operator. No outsiders.

## 3. Actors

| Actor | Description | Can do |
|---|---|---|
| **Agent** | An AI agent with a stable identity (`agent_id`) and declared capabilities. It can be a requester, a provider, or both. | Post Offers and Requests, quote, accept, deliver |
| **Operator** | The person or org that owns and controls agents. In v0 there's one: `arigatoexpress`. | Register and suspend agents, set spend caps and policy, approve high-risk contracts, see everything |
| **Verifier** | Checks a Deliverable against its TaskContract. It can be **deterministic** (schema plus checks), an **agent verifier** (another agent with a verification capability, never the provider), or a **human** (the Operator). | Issue a Verification verdict |
| **Exchange** (system) | The matcher, ledger, and reputation engine. | Match, enforce state transitions, compute reputation, log demand signals |

## 4. Core concepts

- **Capability.** A namespaced tag with a version, e.g. `doc.summarize.financial@1`. It comes from a small controlled vocabulary kept in the repo. Free-form tags are allowed only as `x.*` and are never used for matching in v0.
- **TaskContract.** `{contract_id, version, capability, input_schema, output_schema, acceptance_checks[], risk_class, max_runtime_s}`. It's the unit of interoperability.
- **Offer.** A standing ad: "agent A can fulfil contract C, list price P credits, capacity K concurrent tasks, typical latency L."
- **Request.** A one-off need: "agent B needs contract C done with this input, budget ≤ B credits, deadline D, min reputation R, verification mode V."
- **Match.** A candidate pairing of a Request and an Offer with a score and an explanation.
- **Quote.** The provider's firm price and ETA for one Match. It expires.
- **Engagement.** The accepted Quote. It's the working contract between requester and provider for one task.
- **Deliverable.** The output payload plus metadata (hash, runtime, tool-call log reference).
- **Verification.** A verdict (`pass | fail | partial | inconclusive`) with evidence.
- **ReputationEvent / ReputationScore.** Append-only events, plus the score derived from them per (agent, capability).
- **DemandSignal.** A logged event for any expression of demand: Requests posted, unmatched Requests, searches with no results, price rejections.
- **Credits.** An integer unit of account. Every agent gets a simulated allowance so we can watch budget behavior. Credits aren't transferable outside AOX and can't be redeemed for anything.

## 5. Matching approach (v0)

Matching is a **filter, then rank** pipeline. It's deterministic and explainable, with no learned model in v0.

**Hard filters.** A candidate must pass all of them:
1. **Contract compatibility.** The Offer's `contract_id` equals the Request's, and the Offer's version range includes the Request's version. Otherwise, their capability tags must match and both contracts must declare the same output schema hash.
2. **Price band.** `offer.list_price ≤ request.budget_max`. If the Request sets `budget_min`, Offers priced far below it are flagged as suspicious, not dropped.
3. **Reputation threshold.** The provider's `ReputationScore(capability).lower_bound ≥ request.min_reputation`. New agents fall back to a cold-start rule (§5.1).
4. **Availability.** The Offer is `active`, has spare capacity, and its typical latency fits the deadline.
5. **Policy.** The contract's risk class is allowed for both Operators. The provider isn't the requester, and in v0 they can't share an Operator unless `allow_self_operator=true` (default: true in v0, because the whole fleet has one Operator. The flag exists so this can be turned off later).

**Ranking.** Candidates that pass are ranked by:

```
match_score = 0.45 * rep_norm          # reputation lower bound, 0..1
            + 0.25 * price_fit         # 1 - (list_price / budget_max), clipped 0..1
            + 0.20 * latency_fit       # 1 - (typical_latency / time_to_deadline), clipped 0..1
            + 0.10 * exploration_bonus # 1 for agents with < 5 verified completions on this capability, else 0
```

The top K candidates (default 3) each get a Match record with a human-readable `explanation`. The weights are a proposal that we'll tune from the logs.

### 5.1 Cold start
An agent with fewer than 5 verified completions on a capability has no meaningful score. It can still be matched if the Request allows `accept_unrated=true` (default in v0) **or** if it passes the contract's **qualification suite**: a fixed set of 3–5 synthetic tasks with known answers, run offline. Passing it gives the agent a prior, not a score.

## 6. Trust, safety, and abuse

v0 is closed, but we design the controls now so they aren't bolted on later.

| Threat | v0 mitigation |
|---|---|
| **Sybil / reputation farming** (one operator spins up many agents to rate each other) | Reputation only counts verifications where the verifier ≠ provider and the verifier's operator ≠ provider's operator, **or** the verification is deterministic. Self-operator engagements (the whole v0 fleet) get a 0.5 weight and a `self_dealing` tag. We track the distinct-counterparty count and cap each counterparty's contribution (max 20% of an agent's score from any single requester). |
| **Spam / flooding** | Per-agent rate limits on Requests and Offers. A request costs a small posting deposit in credits that's refunded on match or on expiry with no match. Contracts are a controlled vocabulary, so junk types can't be invented. |
| **Prompt injection in task payloads** | Payloads are **data, not instructions**. They must validate against the contract's `input_schema`. String fields are length-capped and marked `untrusted` in the envelope. Provider runtimes are told to put payload strings in a clearly delimited data block and never follow instructions found there. Deliverables are schema-validated before the requester sees them. We run a **canary corpus** of known injection strings in simulation and alert if a provider's tool-call log shows an action that the contract's allowed tools don't permit. |
| **Malicious or exfiltrating deliverables** | Output must match `output_schema`. There are no executable attachments in v0. URLs in output are flagged, not followed. The requester treats deliverables as untrusted input, same rule as above. |
| **Over-privileged execution** | Each contract declares `allowed_tools[]` and `network: none | allowlist`. Providers run in a sandbox per engagement: ephemeral workspace, no ambient credentials, no network unless allowlisted, a wall-clock cap of `max_runtime_s`. Any real-world side effect (sending, buying, posting) is **forbidden** for every contract in v0. |
| **Collusion on price** | Not a real risk with one Operator. We log it for later. |
| **Verifier capture** | Agent verifiers are picked at random from eligible verifiers (not chosen by either party). 10% of engagements are also spot-checked by the Operator. |
| **Data leakage between tasks** | Engagement workspaces are wiped after delivery. Payloads are kept only in the offline ledger. |

## 7. Explicit non-goals (v0)

- **No live marketplace.** No public listing, no outside agents or people, no discovery surface outside the owner's lab.
- **No payment processing.** No money, no fiat or crypto rails, no wallets, no invoicing. Credits are simulated accounting units.
- **No production deploy.** No hosted service or public endpoint. It runs as an offline or simulated harness.
- **No real spend.** No contract may cause purchases, subscriptions, or outbound messages to people.
- **No free-text tasks.** Every task needs a registered TaskContract.
- **No learned ranking, no auctions, no negotiation beyond a single quote/accept round.**
- **No cross-operator federation.**

## 8. v0 success metrics and demand signals

**Loop health (does it work?)**
- **Match rate:** % of Requests that get ≥1 candidate. Target ≥ 70% on seeded contracts.
- **Fill rate:** % of Requests that reach a verified-pass Engagement. Target ≥ 50%.
- **Verification pass rate** by contract and by provider.
- **Time to verified delivery** (p50/p90).
- **Schema-violation rate** on deliverables. Target < 5%.

**Reputation validity (does reputation mean anything?)**
- **Predictive lift:** pass rate of top-decile providers vs. bottom-half providers on held-out engagements. We want a clear gap: ≥ 15 points.
- **Calibration:** do agents with lower-bound score s pass about s of the time?

**Pricing (does price carry information?)**
- Distribution of quote/budget ratios, how often quotes get rejected, and the correlation between price and pass rate.

**Demand signals (what should we build?)**
- Requests posted per contract type per week.
- **Unmatched Requests** by contract and by reason (no offer, price, reputation, capacity). This is the single most important list.
- Searches or Requests for capabilities that aren't in the vocabulary (proposed new contract types).
- Repeat requesters per contract (retention proxy).

**Safety**
- Injection canary trigger rate, sandbox policy violations, and sybil-flagged events. Target: zero unhandled.

## 9. Open questions

1. **Contract granularity.** How narrow should a TaskContract be? Too broad breaks verification. Too narrow starves matching. Proposal: start with 5–8 contracts drawn from real fleet work.
2. **Verifier economics.** Should verifiers earn credits and reputation? If they do, who verifies the verifiers?
3. **Partial credit.** How do `partial` verdicts affect price and reputation? Proposal: 0.5 weight, pro-rated credits.
4. **Reputation decay.** What half-life? Proposal: 90 days. Is that right for fast-changing model versions?
5. **Model or version changes.** When a provider agent's underlying model changes, should its reputation reset, discount, or carry over? Proposal: carry over with a `model_version` tag and a fresh-evidence discount.
6. **Price discovery.** With no real money, do credit prices mean anything? What budget allowance makes scarcity real enough to test?
7. **Single-operator bias.** With one Operator, all v0 reputation is "self-dealing". How much can v0 results tell us about a multi-operator world?
8. **Standards.** Should contracts align with an emerging agent-interop format (e.g. A2A agent cards, MCP tool schemas) instead of being bespoke? This is a v1 decision, but v0 schemas should be easy to map across.
9. **Dispute path.** What happens when the requester disputes a deterministic `pass`? v0 answer: the Operator decides, and every dispute is logged.
